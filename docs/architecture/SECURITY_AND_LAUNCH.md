# Security, deployment, and launch readiness

## Security controls present in the active backend

- Password hashes use bcrypt; signed access/refresh JWTs are delivered only in HTTP-only cookies. Signup, login, and refresh responses do not include the access token in JSON.
- Refresh-token rotation/reuse handling now persists only SHA-256 digests in PostgreSQL; rotation atomically claims the old digest and stores its successor, while replay revokes the user's remaining sessions. Existing rows were hashed in place on the configured development/testing Neon database; staging/production migration remains pending.
- Password reset tokens are random, stored as hashes, expire after one hour, and atomically replace the password while revoking refresh tokens.
- Mail delivery logs omit email recipients, subjects, verification codes, and reset links. Verification, password-reset, and welcome messages use a durable Postgres outbox with encrypted payloads, expiry/current-token checks, leased claims, and bounded retries. The authenticated verification page can inspect the current message state; `SENT` means the SMTP provider accepted the message, not that it reached the inbox.
- Password changes require the current password, enforce the same complexity as signup/reset, and revoke all refresh tokens.
- OTPs are random, stored as HMAC digests, limited to five attempts, and resend/verification routes are throttled. The implementation supports stored legacy plaintext OTPs during rollout; clean up that compatibility after old rows have expired.
- Instagram OAuth state is signed, audience/issuer-bound, and expires after ten minutes.
- Instagram OAuth state is also bound to a short-lived HTTP-only browser cookie and consumed on callback; callback linking rechecks verified/deletion-locked user state before and inside the serializable account-link transaction.
- New Instagram token writes use versioned AES-256-GCM with a random nonce and authentication tag. Existing CryptoJS AES values remain readable during rollout; the next OAuth exchange/token refresh rewrites them in the new format.
- Meta webhook signatures are checked against the raw request body with constant-time comparison.
- Meta Business Login callbacks validate a bounded, recent `signed_request` with HMAC-SHA256. Deauthorization retries are deduplicated before pausing the matching account and clearing its local token. Data-deletion callbacks drain that account's work, remove account-owned data, and return an opaque status URL/code; callback registration, deletion scope, retention, and live delivery still need staging verification.
- Because production auth cookies must use `SameSite=None` for the separately hosted SPA, API mutations require an allowed `Origin` when access/refresh cookies are present; origin-less bearer clients remain supported. Meta's webhook endpoint is protected by its HMAC signature instead.
- Helmet is enabled; CORS uses explicit configured origins with a localhost fallback.
- Production env validation now refuses placeholder/missing Meta, Razorpay, SMTP settings, insecure cookies, plaintext Redis transport, PostgreSQL URLs without explicit TLS modes, non-HTTPS API URLs, or localhost CORS origins.
- Mutating user actions generally scope account/automation ownership in service methods; protected product routes also require verified email.
- Automation plan gates run on create/edit, go-live, webhook matching, and again before sending or running a delayed follow-up. Expired paid features are skipped and written to the delivery log.
- Follow-up sends have their own idempotent monthly/daily quota reservation and run record. Retry exhaustion marks an unconfirmed follow-up delivery `UNKNOWN` instead of silently dropping it.
- Account caps are rechecked when linking, activating, matching, and sending. After downgrade, oldest active accounts retain slots; over-cap accounts show plan-limited health and incoming matches are logged as skipped.
- Payment verification now validates HMAC format/signature, Razorpay order ownership and exact amount/currency, captured payment status, and unique payment/order IDs before granting plan time. A raw-body HMAC-verified `payment.captured` webhook shares the same checks and transactional idempotency so a lost browser return does not strand a captured payment. Same-order callbacks that observe a concurrent commit are treated idempotently. If capture arrives after account deletion starts, the verified financial record is retained without an attached user or restored entitlement; browser verification reports that no plan was applied. Plan expiry extensions use serializable transactions with bounded write-conflict retries, preventing distinct concurrent orders from overwriting a paid extension.
- Automation button URLs accept only HTTP(S) destinations without embedded credentials; tracked redirects revalidate stored destinations. Per-contact click attribution is HMAC-signed over the link slug and contact ID using a domain-separated key derived from `ENCRYPTION_KEY`; unsigned or tampered attribution still redirects but records only an aggregate click.

## Confirmed issues corrected in this onboarding pass

1. `test-redis.js` contained a literal Redis credential and wrote a key. The current script now requires `REDIS_URL`, only pings, and closes the client. A local comparison confirms the credential-bearing script exists in all 13 reachable commits. The current ignored `.env` and `.env.bak` point to a different Upstash database and their configured password does not match the historical value. This is evidence of a config/database change, not proof the old credential was revoked. **Verify the old database/token is disabled at Upstash, review provider logs and remote repos, then run the full-history CI secret scan before production use.** Do not publish or copy either credential into reports.
2. Payment verification previously defaulted to Pro if Razorpay order lookup failed and did not check captured payment/amount/currency. It now fails closed and stores successful applications idempotently.
3. Monthly and per-automation daily DM quota claims use conditional database updates and UTC boundaries. A unique reservation per provider event makes retries reuse the claim if queue insertion fails. Confirmed sends consume the reservation; definitive skipped/failed sends refund only the original still-live counter windows; `UNKNOWN` delivery remains counted to avoid giving free capacity when Meta may already have delivered it. The settlement migration is applied to development/testing Neon; staging verification remains open.
4. Webhook and delayed worker paths now skip inactive Instagram accounts.
5. Multiple premium features were shown despite no working backend behavior. The new automation page no longer offers AI matching, follower gating, email capture, or image/video blocks; server validation rejects unsupported matching/gating settings.
6. Deployment initially omitted the required long-running queue/token-refresh worker. `render.yaml` now declares one.
7. Concurrent refresh requests could previously both reuse the same refresh-token row. Rotation now claims it conditionally and creates the successor in one transaction; password reset and session revocation also share one transaction.
8. Follow-up sends previously bypassed monthly/daily DM counters and had no customer-visible outcome record. Each eligible follow-up now reserves quota idempotently and records pending, sent, skipped, failed, or unknown state.
9. Instagram OAuth state previously was not bound to the browser that started account linking, and an in-flight callback could outlive an account deletion request. The callback now requires the matching short-lived HTTP-only cookie and rechecks account state before provider exchange and inside the link transaction.
10. Signup, login, and refresh previously also returned the access token in JSON while setting HTTP-only cookies. The frontend uses cookies only; those responses now omit the token.
11. The mutation-origin exception previously accepted missing `Origin` headers even when auth cookies were present. Cookie-authenticated state changes now fail closed without an allowed `Origin`; origin-less non-cookie clients remain supported.
12. Webhook receipts previously had no operator redrive path. The active app now offers a persisted-role ADMIN-only metadata list and rate-limited redrive endpoint, with redrive actor/time fields and durable queue-recovery behavior.
13. Dead-letter payloads could be retained indefinitely. A daily configurable purge now removes old payload JSON while preserving the event receipt for deduplication; redrive claims also reject a payload concurrently purged by the sweep.
14. A successful public comment reply could be repeated when its following DM transiently failed, and network/HTTP 5xx send failures were treated as permanent. Confirmed comment reply attempts are now persisted per run, and transport, HTTP 408/429, and HTTP 5xx errors use worker retry/backoff; a crash between provider acceptance and database persistence remains an exactly-once limitation.
15. Trial reminders could use stale scheduler candidates after a user upgraded or began account deletion. The reminder claim now atomically rechecks the current free plan, deletion state, reminder flag, and trial window before sending; failed delivery releases only a still-eligible claim.
16. Worker availability had no application-level signal. The worker now refreshes a short-lived Redis heartbeat; a verified-admin endpoint and operations card show heartbeat age, queue counts, oldest waiting-job age, and delayed-job due/overdue age without exposing job payloads. External alert routing and threshold-based alerting remain unconfigured.
17. The automation update path previously sent follow-up steps as invalid nested automation data and deleted/recreated all steps, breaking IDs held by delayed jobs. Follow-up edits now preserve existing row IDs, create/delete only changed steps in the transaction, and reject IDs not owned by the automation.
18. The unknown-email login path used a malformed bcrypt placeholder that returned almost immediately rather than performing a password-cost comparison. It now uses a valid cost-12 dummy hash, and the auth test verifies both the encoded cost and that unknown-user login invokes the compare.
19. SMTP transport security was always set to plaintext/STARTTLS mode, even on implicit-TLS port 465, and port 587 did not require STARTTLS. The mailer now enables implicit TLS on 465 and requires STARTTLS on 587; transport-option tests cover both.
20. Automation deletion previously removed database rows while BullMQ could still hold delayed follow-up or active send jobs. Deletion now pauses matching, removes pending/delayed jobs for that automation, waits up to fifteen seconds for active jobs, and leaves it paused if the queue is unavailable or work does not drain. Worker checks prevent sends and follow-up scheduling after pause; unit tests cover scoped cleanup and queue failure.
21. Verification, reset, and welcome mail was previously attempted inline after account state changes, so SMTP outages or process restarts could lose messages. Those messages are now written transactionally to an encrypted Postgres outbox, retried by the worker, and canceled when their token is stale or expired. Signup now also commits its initial refresh session in the same transaction as the user and verification mail, preventing a persisted account with a failed signup response if session creation fails. This adds a migration that still requires staging validation; SMTP delivery can still be duplicated if the provider accepts a message and the worker crashes before recording success.
22. Refresh JWTs were stored in plaintext in PostgreSQL. New writes now store SHA-256 digests, and a migration hashes existing session rows in place to preserve valid sessions. The migration is applied to the configured development/testing Neon database; staging and production still require their own schema/history review and rollout.

## Potential risks needing targeted review

- The frontend sets framing, MIME-sniffing, referrer, and permissions headers but no Content-Security-Policy. Next.js nonce-based CSP requires request-time rendering, which changes currently prerendered routes and may affect cache/hosting cost. Measure that tradeoff and test policy compatibility with inline styles, the configured API origin, and Razorpay Checkout before enforcing it; no unsafe HTML rendering from user-controlled data was found in the source search performed for this review.
- Fastify trusts one proxy hop for client IP derivation. Confirm the actual Render proxy chain reports the visitor IP correctly; adjust only to the documented trusted hop count if needed.
- OAuth, token-refresh, media, payment, and Meta send logs record HTTP status plus filtered provider codes instead of raw provider messages. Worker logs and stored webhook/retry errors use bounded class labels, not raw exception text. Continue reviewing logs before external security review; never log tokens, authorization codes, or full request payloads.
- The global HTTP limit (120 requests per minute per tracker) and route-specific auth/profile limits use an atomic Redis sliding window; tracker keys are SHA-256 hashed before storage and the store fails closed when Redis commands fail. The Instagram webhook verifies Meta's HMAC signature, accepts a bounded 5 MiB body, and valid signed deliveries bypass the generic IP throttle so shared provider traffic is not capped by unrelated tenants. Failed signatures increment a short-lived Redis counter keyed by a SHA-256 hash of the requester IP (30 failures per 60 seconds, then 429). Edge-level abuse controls, Redis outage behavior, and staging/load validation remain open.
- Webhook batches are persisted with one database insert before ACK and eligible events are bulk-enqueued; pending receipts are reconciled from Postgres every 10 seconds. Handler attempts use backoff and dead-letter at eight; an admin-only API and dashboard redrive UI exist. Alerting and an operator runbook are still missing.
- Dead-letter payloads may contain Instagram user content. A daily sweep now purges expired payloads after `WEBHOOK_PAYLOAD_RETENTION_DAYS` (1–365; default 30) while preserving receipt IDs for deduplication. Purge timing and the selected production retention value still need staging verification; other idempotency tables have no retention policy.
- Worker retries can resend after a crash between Meta accepting a message and the DB recording SENT. Confirmed public comment replies are persisted to suppress duplicates on later DM retries, but crashes before that marker commits remain ambiguous; exactly-once external delivery is not guaranteed.
- Existing legacy token ciphertext has no authentication tag and remains in the database until that account next refreshes its token. Confirm a migration plan and key backup before changing `ENCRYPTION_KEY`.
- The worker and activation path reject legacy automations with unsupported `askToFollow` or `collectEmail` settings and record matches as skipped rather than sending. A read-only aggregate check found zero such automations in development/testing Neon; inventory staging/production and guide affected customers to edit or replace those automations before rollout.
- Legacy users with `plan=PAID` and no `planExpiresAt` are treated as indefinitely Pro by `paidTier`; an aggregate read-only check of development/testing Neon found one legacy `PAID` row, with an expiry, and zero `PAID` or named paid-tier rows missing expiry. Staging/production counts and billing reconciliation remain required before paid traffic.
- Comment private replies reserve a shared Redis rolling-window slot per Instagram account, capped at 700/hour against Meta's documented 750/hour limit; saturated jobs defer without using a retry. This does not pace ordinary direct messages or follow-ups per account. Queue concurrency is global per worker, so verify the account-level behavior and provider responses in staging before launch.
- User-scoped JSON export and staged self-service account deletion are available in Settings; deletion is also available from the email-verification screen for unverified signups. The JWT-authenticated deletion route requires current password and account-email confirmation but not verified email. It immediately tombstones profile/login fields and clears local Instagram credentials, then removes account data after queue drain while detaching transaction records. Provider-side token grant revocation, staging behavior, backup/restore, retention schedules for other customer data, incident response, and audit-log policy remain unverified or absent.
- Unverified signups are automatically tombstoned after the configurable `UNVERIFIED_ACCOUNT_RETENTION_DAYS` period (default 30 days), sessions/tokens are revoked, and final removal follows the existing 15-minute queue-drain path. The period is disclosed in the draft Privacy Notice but requires owner/counsel confirmation before production signup is enabled.
- A GitHub Actions workflow scans checked-out files and all reachable Git history with Gitleaks on pull requests, pushes, manual dispatch, and weekly schedule. It uses a full-depth checkout, pins the scanner image by digest, limits token permissions to repository read, and redacts findings. The history scan has not run in CI; the known Redis credential was present in all 13 locally reachable commits, so provider rotation and a controlled remote history/repository review remain required. Ignored local environment files are outside the workflow's checkout scan. Dependency audit reported zero advisories in backend and frontend lockfiles on 20 November 2026.
- The worker writes a short-lived Redis heartbeat. A verified ADMIN can read heartbeat freshness, queue counts, oldest waiting-job age, and delayed-job due/overdue age through the operations page and `/api/admin/health/worker`; external alerting and threshold-based notification are not configured.

## Deployment as checked in

`render.yaml` declares:

1. `relayo-api`: Render free web service rooted at `backend-nest`; build uses `npm ci`, generates Prisma Client, and compiles; start deploys Prisma migrations then starts HTTP API. Render checks `/ready`, which verifies PostgreSQL and Redis within a short timeout; `/health` remains a process liveness endpoint.
2. `relayo-worker`: persistent Render background worker, same backend build, runs `npm run start:worker` for BullMQ sends, daily token refresh, and mail outbox processing. It uses the API service's environment values. This may incur continuous service cost; consult current Render pricing before applying the blueprint.
3. `relayo-frontend`: Render free web service rooted at `frontend`, uses `npm ci`, and runs the Next.js production server.

Required secrets/config include PostgreSQL direct/pooled URLs, Redis URL, JWT secrets, encryption key, Meta app credentials/webhook token, Razorpay keys and a 32-character minimum Razorpay webhook secret, SMTP credentials, public API URL, exact CORS frontend origin, and frontend `NEXT_PUBLIC_API_URL`. `.env.example` files document local shape. Never commit local `.env` files.

The public site sets `metadataBase` from `NEXT_PUBLIC_SITE_URL`, then Render's `RENDER_EXTERNAL_URL`, then a localhost development fallback. Set `NEXT_PUBLIC_SITE_URL` to the canonical custom domain in the frontend service before production builds if the product is served from a custom domain; social preview URLs are build-time metadata.

The API start command runs `prisma migrate deploy`. The contact migration was fixed before rollout to add its outbox relation column before the unique index and foreign key. Validate the migration sequence against staging, including data compatibility and runtime behavior, before production rollout. No staging/production database was changed.

The API, worker, and frontend are pinned to Node 24.22.1 in `render.yaml`; package manifests constrain both apps to Node 24. Builds were checked locally on Node 24.13.1, but the pinned Render runtime has not been deployment-tested. The root `docker-compose.yml` now starts local Postgres, Redis, Mailpit, active Nest API, worker, and frontend; `frontend/Dockerfile` builds the Next standalone server.
