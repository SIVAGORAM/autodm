# Development roadmap

This roadmap is ordered around launch risk and creator trust, not implementation convenience. It reflects repository evidence; it does not assume market demand or revenue.

## Phase 1 — prove safe core delivery

1. **P0: rotate exposed provider credentials before production.** A redacted local scan confirmed that commit `4d2cf8ebdb68` contains a credential-shaped Redis URL in `test-redis.js` line 4; the commit is reachable from both local `main` and `origin/main`. The current tracked script reads `REDIS_URL` from the environment. `.github/workflows/secret-scan.yml` runs redacted Gitleaks scans over checked-out files and reachable Git history on pushes, pull requests, manual dispatch, and weekly schedule, but no hosted run result was available in this review. This local scan does not cover remote-only refs, repository copies, logs, or forks. Verify the Redis credential was revoked/rotated in Upstash and review provider access logs; then review successful hosted scans and remote/fork cleanup before production use. Treat it as compromised until provider-side rotation is confirmed. The Cloudinary API secret was also shared in project chat; rotate it in Cloudinary and update local/production secret stores directly without committing or pasting the replacement into chat. Verify avatar upload and cleanup in staging.
2. **Development/test Neon migration chain: migration 33 is applied.** A direct read-only `prisma migrate status` check on 2026-11-23 first found only `20261123150000_public_profile_reporting` unapplied. The additive migration was applied to the configured development/testing database, and a follow-up status check reported all 33 migrations applied and the schema up to date. Migrations 1–32 were previously applied; the earlier verification recorded 3 refresh-token rows with 3 distinct families and no missing IDs. No staging or production database was accessed. Staging/production remain unverified: compare each ledger/schema and test old-account compatibility before rollout. Do not use `db push --force-reset`.
3. Run a Meta test-user flow through OAuth, account-cap enforcement, webhook signature, comment/DM matching, retry, token refresh, disconnect, and plan expiry. Confirm only reviewed scopes and supported media types.
4. Complete Meta integration rollout: Unified Login and opt-in 60-day BISU token refresh code are implemented behind environment flags; refresh has not been tested against an authorized Meta staging account and stays disabled by default. Live-comment intake/delivery is opt-in behind `META_LIVE_COMMENTS_ENABLED=false`; the Render worker now inherits the same flag as the API, and focused automation/webhook/subscription tests pass, but no authorized live-broadcast test exists. Next validate the exact Meta app/configuration, complete Advanced Access, and pass controlled OAuth, expiry, Reel/webhook, and private-reply tests. Cross-mode dual-token migration/rollback remains outstanding. Existing legacy integrations have no announced end date. See `META_LOGIN_MIGRATION.md`.
5. Exercise email verification/reset/trial reminders and Razorpay sandbox order/verification/refund scenarios. Verification users can now inspect queue/retry/SMTP-accepted/failure status; complete SMTP staging acceptance and add operator alerting for terminal failures. Define payment support/reconciliation procedures.
6. **P0: remove the sleeping Render API from the production path.** `render.yaml` declares `relayo-api` and the Render frontend on the free plan. Render's official docs say free web services sleep after 15 minutes without inbound traffic, can take about a minute to wake, and are not for production. Select an always-on production API host/plan and confirm frontend hosting behavior before public launch; no service plan was changed. Review current [Render pricing](https://render.com/pricing) and get owner approval before incurring compute costs. Then validate the pinned Node 24.22.1 runtime, service environment references, one-hop proxy IP behavior, persistent worker cost, auto-deploy and migration sequence.
7. Connect external monitoring to API readiness and the admin worker-health signal; add alerts for queue age/dead letters, token refresh failures, payments, SMTP, and service outages.

## Phase 2 — complete launch operations and trust

1. Replace the Terms/Privacy/Refund drafts with owner- and counsel-approved text; confirm legal entity, support/grievance contacts, subprocessors/regions, retention, and refund eligibility before setting legal policy status to `APPROVED`.
2. Verify export and staged account-deletion behavior against staging; define broader retention, backups, restore drills, incident response, access review, provider-side token revocation, and customer support/refund processes.
3. Complete public-profile abuse operations before public launch: review the additive report migration on an isolated Neon branch, set a moderation policy and escalation owner, verify admin permission assignment, report throttling, profile hiding, audit retention, and privacy disclosures in staging. The report form and review queue are implemented in the current tree; hosted schema and browser acceptance remain outstanding.
4. Complete dead-letter and `UNKNOWN` delivery operations with alerting, idempotency checks, and user-visible delivery guidance. The admin UI/API for webhook receipt redrive and an operator runbook now exist.
5. Validate follow-up run/quota lifecycle and automation-delete queue cancellation in staging; add safe operator redrive for failed/unknown deliveries only after duplicate-delivery safeguards are established.
6. Validate the implemented downgrade policy in staging: oldest active accounts retain plan slots, while automations on accounts outside the cap are skipped and marked plan-limited. Review reconnection behavior and ensure billing/help copy explains the policy.
7. Extend isolated PostgreSQL/Redis CI smoke coverage. The current `.github/workflows/ci.yml` applies migrations to disposable PostgreSQL, starts PostgreSQL and Redis services, and runs the audit immutability, auth/payment, dashboard-event, signed webhook-intake/idempotency, and Redis throttler smoke scripts. The auth smoke checks cookie flags, paths, lifetimes, hashed persistence, CSRF-origin rejection, and now races two refreshes while verifying replay invalidates only that device and a second device remains refreshable. Its direct Prisma client now uses the same PostgreSQL driver adapter as the application. These checks are wired into CI; no hosted GitHub Actions result was available in this review. The webhook smoke verifies durable receipt, then runs the production BullMQ worker dispatcher against a selected-media comment and deterministic Meta stubs. It checks keyword matching, quota reservation, send-job completion, and successful delivery state without an external send. It now also injects out-of-order comment-reply message timestamps and asserts that the database retains the newest timestamp and the comment follow-up remains delayed from it. The updated auth smoke passes Node syntax checks but has not run against PostgreSQL/Redis in this workspace; CI owns its database-backed execution. Further add worker-restart/recovery behavior, payment entitlement/race cases, quota concurrency, ownership, account-link, and full deletion queue-drain coverage; then validate provider-dependent behavior in sandboxes.

## Phase 3 — improve creator activation and retention

1. Complete responsive and keyboard/screen-reader review across landing, auth, onboarding, automation builder, logs, and billing.
2. Complete guided onboarding, account health, a controlled provider test-send workflow, clearer plan/usage warnings, and actionable provider-permission explanations. Account health is partial: Instagram shows webhook status and near-expiry token warnings with a reconnect action where supported; worker health is visible to verified admins. The local sample-recipient message preview is implemented in create/edit screens.
3. Improve analytics and creator outcome tracking before adding broad AI/CRM features.
4. Expand the basic contact inbox toward CRM only with validated user demand, consent and retention controls, segmentation/attribution needs, operational cost, and Meta policy fit. Evaluate AI intent, consent-based email capture, workspaces, and collaboration against the same criteria.

## Release gates

Do not call the product launch-ready until P0 items in `SECURITY_AND_LAUNCH.md` pass with recorded evidence. Do not advertise any feature marked planned, disabled, or provider-unverified in `FEATURE_INVENTORY.md`.

## Latest local verification (2026-11-23)

- Backend: `npm test -- --runInBand` passed all 76 suites and 597 tests; `npm run build` passed. Coverage includes the comment-follow-up latest-reply delay, worker deferral, queue dispatch validation, and Redis eviction-policy enforcement.
- Worker dispatch hardening: `processDmQueueJob` now accepts only the durable webhook and `send` job names; malformed webhook receipts, invalid send payloads, and unknown queue entries are discarded before they can reach delivery processing. Its focused suite passes 5/5 tests, and the Nest production build passes.
- Super Admin bootstrap guard: the one-time role-provisioning CLI requires an exact database host/name confirmation and an additional `--allow-production` flag when `NODE_ENV=production`. CI now runs this isolated check; it does not instantiate Prisma or connect to a database.

Production API readiness now checks Redis `INFO memory` for `maxmemory_policy:noeviction`, and the worker fails startup if the policy is absent, unsafe, or unreadable.
