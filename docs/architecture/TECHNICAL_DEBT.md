## P1 — reliability and creator trust

- Login now verifies `/api/auth/me` after successful password/MFA authentication before entering the dashboard, avoiding a confusing apparent-success redirect when browser session cookies are unusable. This is source/build verified only; test cookie delivery on the actual frontend/API domains. Render keeps `autoDeploy: false`, so deploy the frontend and API together after the approved staging checks.
- Meta delivery cannot be made exactly-once across provider acceptance and database writes. `UNKNOWN` runs now expose ambiguity, but there is no safe redrive workflow. Confirmed optional public replies are marked to avoid repeating them on later DM retries; a worker crash between Meta acceptance and saving that marker can still leave an ambiguous outcome.
- Follow-ups now have separate run records and reserve monthly/daily quota idempotently; definite no-send outcomes refund quota, while unknown outcomes remain counted. Automation deletion reconciles unstarted reservations after removing pending jobs. There is still no safe delivery-run redrive or per-recipient cancellation history.
- **Comment follow-up delay race fixed in code:** out-of-order message webhooks now schedule from the contact's latest persisted `lastReplyAt`, and the DM worker rechecks the configured delay at send time, re-delaying early jobs. Regression coverage exercises stale webhook timestamps and worker deferral. The full local backend suite and build pass; concurrent staging delivery and Meta timing behavior remain unverified.
- Per-contact tracked-link attribution is now signed over the link slug and contact ID; altered or legacy unsigned values still redirect but no longer attach clicks to a contact. Previously delivered unsigned links retain aggregate click counts but lose contact-level attribution; changing `ENCRYPTION_KEY` also invalidates signed attribution while redirects remain functional.
- Webhook dead-letter rows now have an admin-only metadata list/API and dashboard redrive UI with actor/timestamp tracking. Selected-media comment lookup failures now propagate into the durable webhook retry/dead-letter path; an account-wide fallback is not sent while the source post remains unknown. A daily configurable retention sweep purges old payloads while retaining deduplication receipts. A pre-launch operations runbook exists, but it has not been exercised in staging; automated alerting and production retention verification remain absent.
- The new `20261122210000_admin_audit_immutability` migration rejects UPDATE, DELETE, and TRUNCATE on privileged-action audit records while allowing only the foreign-key `actorId` nulling needed when an account is deleted. CI now includes a disposable-Postgres smoke check. This protects against ordinary application-role mutations, not a database owner who can disable triggers; hosted migration and an independently retained audit export remain launch checks.
- Verification, password-reset, and welcome mail now use an encrypted transactional Postgres outbox with expiry/current-token checks, leased worker claims, bounded retries, and 30-day terminal-row cleanup. The verification screen can inspect the authenticated user's current OTP queue/retry/SMTP-accepted/failure state; an admin-only redacted outbox dashboard exposes aggregate counts and message status. Reset/support messages still lack customer-visible delivery status, and external alerts/admin redrive are not configured. SMTP now uses implicit TLS on port 465 and requires STARTTLS on 587. The migration, worker retry behavior, and live SMTP remain unverified in staging; SMTP acceptance followed by a worker crash can still produce duplicate email.
- After plan downgrade, the oldest active accounts keep plan slots; automations on over-cap accounts are skipped and show a plan-limited health state. Billing/help copy should continue to explain this behavior clearly.
- Trial-ending reminder claims now recheck current eligibility atomically and are reset after a mail failure only while the user is still on an eligible free trial; live SMTP behavior still needs staging verification.
- The dashboard now includes a three-step first-automation checklist and monthly DM/active-account meters with an 80% DM warning. The notifications page reports status-load failures and consolidates token warnings at the Instagram-account level. The checklist, notifications, and warning presentation still need authenticated browser testing with representative accounts and near-limit states; notification history/unread state remains a product gap.
- **HTTP throttling now uses shared Redis storage:** Nest's global 120-per-minute limit and route-specific limits use an atomic Redis sliding window; tracker keys are hashed before persistence. Unit tests cover key privacy, return values, malformed responses, and connection cleanup. CI now has an isolated Redis integration check for bucket isolation, sliding expiry, concurrent requests, and block reset; confirm its first hosted run and verify fail-closed outage behavior in staging before launch.
- Instagram webhook batches are persisted and queued in bulk, with a 5 MiB request cap and HMAC validation. Valid deliveries bypass the generic IP throttle to avoid blocking shared Meta traffic; failed signatures use a 30-per-minute hashed-IP Redis counter. Edge-level abuse controls and staging/load verification remain open. Comment-triggered post/reel private replies are proactively capped at 700 per account per rolling hour in shared Redis, below Meta's documented limit of 750 to leave room for external sends. Provider error 80002 still uses BullMQ retry/backoff. Staging verification of Redis timing and provider behavior remains open.
- **Reels and comment follow-up verification:** The editor and API now accept selected owned `VIDEO` media, and webhook event matching, deduplication, and private-reply queueing have code-level coverage. Already-live legacy rules are not automatically paused by a media-type scan, and `ANY_POST` still matches whichever events Meta delivers. Current Meta webhook/private-reply guides describe Reel comment workflows across documented login setups, while an older Facebook Login-specific page says Reels are unsupported. HeyLaunch has no controlled live Reel event. Instagram Login does not expose the documented `media_product_type` field in the media response, so the picker may label a Reel as `Video / Reel` rather than identify its subtype. Matched comment events now fetch Meta's comment-node `timestamp` (and `media` when needed) before quota reservation; the worker enforces the seven-day window from comment creation and fails closed for legacy queued jobs without an authoritative timestamp. Retries with a prior pending send become `UNKNOWN` rather than risking a duplicate. Verify event delivery, commenter identity, one permitted private reply, duplicates, eligibility expiry, rate limits, and failure recovery on an authorized staging account. Comment-trigger follow-ups wait for the commenter's message webhook and recheck the 24-hour window at send time. `NO_REPLY` follow-ups remain unavailable after comment automation because a reply is required first.
- **Meta API migration path:** Unified Login OAuth, account-scoped API routing, and webhook subscription are implemented behind an environment gate; existing rows remain `INSTAGRAM_LOGIN`. Cross-mode reconnect for the same Instagram account is intentionally rejected because the account row stores one active token, so a safe dual-token migration/rollback flow remains outstanding. Unified token expiry is read from `expires_in` or, when omitted, a validated Meta `debug_token` response. An opt-in BISU refresh path now uses Meta's `fb_exchange_token` endpoint, but remains disabled by default and unverified against staging. Meta recommends Unified Login for new integrations, while current Instagram Login accounts have no announced retirement date. Reel support is documented, but no HeyLaunch live test exists. Do not migrate existing accounts or market reliable Reels until authorized tests pass. Details: `META_LOGIN_MIGRATION.md`.
- **Public profile icon coverage:** Custom-link favicon fetching uses HTTPS only, rejects non-public IPv4 DNS answers (including the IANA special-purpose ranges 192.31.196.0/24, 192.52.193.0/24, and 192.175.48.0/24), pins each request to its validated address, revalidates redirects, limits response bytes and image dimensions, and enforces a 10-second overall discovery deadline in addition to per-hop limits. HTTP-only hosts, IPv6-only hosts, SVG favicons, cross-provider browser previews, persistent distributed cache, and measured CDN cache behavior are not supported or verified; those cases use a fallback icon. Unit coverage exercises blocked ranges, redirects, DNS pinning, deadline handling, image normalization, and cache behavior, but no live external fetch or production load test was performed. The 2026-11-23 IANA-registry follow-up passed all 29 favicon service tests and the Nest build; this remains source/test evidence, not a live-network test.
- `/health` is liveness; `/ready` probes PostgreSQL and Redis and is configured for Render's API check. A Redis worker heartbeat and admin-only operations panel expose queue counts, oldest waiting-job age, and delayed-job due/overdue age; external alerting and threshold-based notifications remain absent.

## P2 — product breadth and maintainability

- Two frontend component systems (`rl-kit` and `ui/primitives`) can drift; no full responsive/accessibility assessment has been completed.
- Public pricing cards remain JSX copy separate from the backend plan catalogue. A Jest consistency check now fails if displayed prices, account caps, monthly DM quotas, or keyword limits drift; a shared plan package would remove the duplication.
- Several legacy API client methods have no active Nest endpoint. Campaign route aliases and the legacy Express source can still mislead new contributors; the root Compose stack now starts the current Nest/PostgreSQL/Redis/worker/frontend topology.
- Analytics is basic run/sent/click aggregation. No conversion attribution, cohort view, analytics export, or performance budgets are implemented.
- CI now applies migrations to fresh PostgreSQL, probes API readiness against PostgreSQL/Redis, and contains API-level auth/payment-signature smoke coverage plus loopback-only authenticated dashboard SSE-to-Redis and signed webhook pipeline smoke flows. The webhook smoke starts the production BullMQ queue dispatcher only after confirming the disposable queue contains its single expected test job; it exercises signed intake, durable receipt, comment keyword matching, quota reservation, worker delivery state updates, and a deterministic Meta stub without external calls. The smoke flows are syntax-checked locally, but their first GitHub Actions execution is not yet verified. Worker restart/recovery behavior, browser-based auth/account linking, payment entitlement/UI, and provider sandbox behavior still lack end-to-end verification.
- Unimplemented roadmap features include AI intent, reliable follower gating, email capture, rich media, workspace/team access, CRM segmentation, lead attribution, and unified inbox. Basic contacts browsing, private notes/tags, and CSV export are now available; do not market a full CRM until those workflows exist.
