SMTP acceptance is not inbox-delivery proof; SMTP delivery and cookie behavior need staging verification |

Staging/production migration and admin acceptance are not verified |

| Account listing/media/disconnect | Implemented in code | Instagram API service/controller; media selection uses 50-item cursor-paginated batches so creators can load older posts. Disconnect pauses automations, removes queued/delayed account jobs, waits for active jobs, then clears the encrypted provider token and expiry while retaining account history for a later reconnect. Queue failure leaves automations paused and the token intact so the owner can retry safely. |
| Meta Business Login deauthorization callback | Implemented in code; staging configuration required | `POST /api/instagram/deauthorize` accepts a bounded form body, verifies a recent Meta `signed_request` HMAC-SHA256 and app-scoped Instagram user ID, deduplicates retries, then atomically pauses automations, disables the matching account, and clears local token data. Callback registration and provider delivery remain unverified. |
| Meta data-deletion callback | Implemented in code; staging configuration required | `POST /api/instagram/data-deletion` verifies the signed request, pauses/disables the matching Instagram account, clears its token, drains active and queued work, deletes the account and its cascaded automation/contact/activity data, and returns an opaque completion code and public status URL. Only a 90-day hashed request receipt and random confirmation code are retained. Meta callback delivery, deletion scope, and status URL are not staging-verified. |
| Automation editing and deletion | Implemented in code | Detail page links to an editor for trigger, matching, public reply, DM/button content, click tracking, and follow-ups. | Post comment keyword automation (photo/carousel/video) | Implemented in code; provider verification required | The builder loads media in 50-item cursor-paginated batches and matches by media ID. New `POST_COMMENT` rules require a selected non-empty media ID; account-wide coverage uses the separate paid `ANY_POST` trigger. Historical `POST_COMMENT` rows with a null media ID still act as account-wide rules and receive the paid-trigger entitlement at list, activation, and delivery checks. On create, update, and activation, the API reads selected media `id,media_type,owner` through the connected account token, verifies ownership, and accepts `IMAGE`, `CAROUSEL_ALBUM`, and `VIDEO`. Instagram Login may not distinguish a Reel from another video in the selector. Intake normalizes `id` and `comment_id` payloads and accepts array-valued comment changes; the worker matches keywords and queues an eligible private reply. Exact-media rules take precedence over `ANY_POST`; same-scope matches use oldest-created rule, then ID. Meta permissions, webhook delivery, App Review/Advanced Access, and a controlled provider test remain unverified. |
| Reel comment keyword automation | Implemented in code; real Meta delivery unverified | The selector labels Meta `VIDEO` media as `Video / Reel` (or `Reel` when `media_product_type` is available), and create/update/activation validate that selected video belongs to the connected account. The webhook processor matches the exact media ID, deduplicates comment events, and queues a private reply through the existing sender. Current Meta webhook/private-reply docs describe Reel comments; an older Facebook Login-specific page conflicts. HeyLaunch has not received a controlled Reel event or confirmed message delivery. Do not claim end-to-end provider verification until authorized staging acceptance passes. See `META_LOGIN_MIGRATION.md`. |
| Incoming DM and story reply triggers | Partially implemented | Message webhooks classify `message.reply_to.story` as `STORY_REPLY` and other incoming text messages as `DM`; the oldest matching live rule wins, then ID. The inbound provider timestamp travels with the queued job. Ordinary DMs and story replies use a fail-closed 24-hour window; a DM gets up to seven days only when Meta's signed webhook includes the documented Click-to-Direct marker (`referral.source=ADS`, `type=OPEN_THREAD`, and a numeric `ad_id`). Follow-ups retain the original event time and are capped to the remaining eligibility window; malformed timestamps are skipped rather than replaced by server time. Ambiguous prior sends remain `UNKNOWN`. Code-level webhook/worker tests cover the ad marker, boundaries, follow-up cap, expired jobs, and retry ambiguity. Permissions, real ad-referral payloads, and live delivery still need authorized Meta staging validation |

| Public creator profiles / link-in-bio | Implemented in code; Cloudinary and browser acceptance required | The authenticated editor at `/dashboard/profile` manages normalized unique usernames, visibility, appearance, biography, social links, custom links, ordering/visibility, and live preview. Public and editor avatars use an initials fallback both when no image is set and when an image URL fails to load. Favicon requests now go through a public same-origin API proxy that pins validated public IPv4 DNS answers, blocks internal/reserved destinations, revalidates every HTTPS redirect, limits time/bytes, rasterizes supported icons to PNG, caches positive/negative results, and falls back cleanly. HTTP-only origins and SVG icons use the fallback; links themselves remain functional. Local backend credentials are configured, but Render credentials and staging upload/public-page acceptance remain outstanding. Analytics and abuse reporting are not implemented. |

## Known implementation gaps to keep visible

- `matchMode=AI_INTENT`, `askToFollow`, and `collectEmail` are rejected for new/update requests because the server behavior was incomplete.
- API DTO no longer accepts image/video blocks; button and text messages are the supported composer surface.
- Plan tiers currently differentiate account/DM/keyword limits and trigger/follow-up access. The legacy `removeBranding` plan flag is disabled because no brand-badge behavior exists. Business claims for agency collaboration or lead management must not be advertised until built.
- Support operations still need an owner, response targets, retention policy, and notification process before launch; analytics remains basic and notifications are browser-generated only.
